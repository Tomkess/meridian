## Summary

`specs/REGISTRY.md` is generated by `rebuild_registry()` and committed to git. It
conflicts on nearly every merge, because every branch that touches a spec
regenerates the whole file. Hand-resolving those conflicts has already dropped
rows — silently, since nothing checks the registry against its sources.

The file is a **cache**. Every row is derived from things that are themselves
tracked: `specs/*/spec.md` frontmatter, `specs/goals/`, and `specs/decisions/`.
So committing it protects no information while guaranteeing conflicts on a file
whose corruption is invisible.

This gitignores it and closes the one real gap that creates: a fresh clone has no
index until something regenerates it, and a skill reading a missing registry sees
no features rather than an error. `meridian guide` now says so.

The alternative considered and rejected was `specs/REGISTRY.md merge=ours` in
`.gitattributes`. It needs `git config merge.ours.driver true` per clone, and
when that is forgotten git does not fail — it merges normally. A fix that fails
silently is worse than none when the injury being fixed is already silent.

## Appetite

`xs` — one ignore rule, one guide check, and the documentation that stops someone
re-adding the file.

## Acceptance Criteria

- **AC1** — `specs/REGISTRY.md` is listed in `.gitignore` and removed from the
  index with `git rm --cached`, while remaining on disk.
- **AC2** — The ignore rule is anchored (`/specs/REGISTRY.md`), so
  `meridian/skills/templates/REGISTRY.md` and the golden fixture's own
  `tests/golden/project/specs/REGISTRY.md` are unaffected.
- **AC3** — `_check_registry()` in `meridian/guide.py` reports a missing
  `REGISTRY.md` as a `warn` with `meridian index` as the next action.
- **AC4** — `_check_registry()` reports a **stale** registry — one whose mtime is
  older than any `spec.md`, goal, or decision it indexes — as a `warn`. Staleness
  is the failure mode that matters once git no longer carries the file.
- **AC5** — A project with a registry and no sources at all is `ok`, not a
  warning: there is nothing for it to be stale against.
- **AC6** — `run_guide()` returns 9 steps with sequential numbers, and
  `meridian guide` renders the new step without any change to `cli.py` — it
  already iterates the returned steps.
- **AC7** — `CLAUDE.md` records that the registry is generated and not tracked,
  with the reason, so it is not re-added by someone who sees an untracked file
  and assumes an oversight.

## Scope

`.gitignore`, `meridian/guide.py`, `tests/test_guide.py`, `CLAUDE.md`.

## Out of Scope

- **Making skills tolerate a missing registry.** They currently read whatever is
  there. The guide warning makes the gap visible to the human; teaching each
  skill to regenerate on demand is a larger change and would hide the gap rather
  than close it.
- **Regenerating the registry automatically on clone.** There is no hook to hang
  that on, and the first spec-mutating command already does it.
- **The other repos.** Meridian is installed into ten projects, each with its own
  committed `REGISTRY.md`. Propagating this decision is a separate call — it
  changes their git history, not just Meridian's.

## Key Risks

- **A fresh clone's skills read no feature index.** Real, and the reason AC3
  exists. The window is one spec-mutating command long, and `meridian guide` is
  the first thing the setup flow tells a user to run.
- **mtime is a weak staleness signal.** A checkout can rewrite mtimes and produce
  a false stale warning. Chosen anyway because the failure it reports is cheap to
  fix — `meridian index` — and a false negative (silently stale index) is the
  expensive one.
